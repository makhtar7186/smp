## 1. Vue d'ensemble

**SMP Gestion** est une application desktop Python/Tkinter de facturation, suivi de ventes et gestion de stock pour la **SOCIÉTÉ DES MATIÈRES PLASTIQUES SUARL** (Diamniadio, Sénégal — devise FCFA).

- **NINEA** : 006569034 2A2

- **Adresse** : Diamniadio, près de l'hôpital des enfants, avant la sortie à péage
- **Téléphone** : 33 897 72 94 / 77 487 07 09

Ces informations sont centralisées dans `app/config.py::ENTREPRISE` et le logo dans `logo.png` (racine du projet) — consommés uniquement par `app/services/pdf_service.py`.

> Note technique : le projet a été adapté à partir d'une base existante développée pour une autre entreprise (mobilier literie). La marque affichée (fenêtres, exécutables `SMP*.exe`, PDF) a été entièrement mise à jour ; seuls des identifiants internes strictement invisibles de l'utilisateur final ont été laissés tels quels (nom du fichier de base de données `app/data/promatelas.db`, préfixe `PROMATELAS_` des variables d'environnement de configuration) — un renommage sans aucun bénéfice utilisateur, purement cosmétique côté code.

**Utilisateur cible** : le gérant et son équipe (postes Windows, usage quotidien hors ligne pour la facturation, en réseau local/Tailscale pour la consultation à distance et le suivi de stock).

**Périmètre V1** :
- Facturation : panier de lignes produits, totaux automatiques (`total ligne = quantité × P.U.`, `total facture = Σ lignes`), **TVA à 18 % obligatoire sur toute facture** (fixe, non modifiable depuis l'interface), numérotation continue auto-incrémentée mais modifiable (jamais de remise à zéro ni de plafond). Enregistrer/imprimer ne vide pas le panier ; seul le bouton « Nouvelle facture » vide le panier et passe au numéro suivant. **Il n'existe qu'une seule sorte de facture** (pas de distinction usine/revendeur — voir section « Règles métier clés »).
- **Brouillons (proforma)** : le panier peut être enregistré comme brouillon **sans numéro de facture**, pour reprise ultérieure — voir section « Proforma ». Un brouillon n'affiche pas de TVA (elle n'apparaît qu'à la validation en facture réelle).
- Bordereau de livraison PDF **à la demande** depuis une facture (mêmes lignes sans prix).
- Historique des ventes consultable, filtrable (période, client), factures réimprimables.
- Référentiels : **produits** (nom d'article + option dimension ou litrage, chacune avec son propre prix — catalogue à plat, voir section dédiée) et **clients** (nom, adresse, téléphone — pas de notion de sous-client/revendeur).
- **Gestion de stock** : suivi de la quantité en stock de chaque article, décrémentée automatiquement à chaque facture, alimentée par des entrées/ajustements manuels depuis une application dédiée — voir section « Gestion de stock ».
- Page **remise annuelle** : CA annuel par client + calcul de remise (taux saisi), historisé.
- Dashboards : KPI (CA jour/mois/année, nb ventes, panier moyen, comparaison N-1), top produits, évolution du CA, répartition par article.
- Interface **trilingue FR / EN / ZH**, commutable à chaud (paramètre persistant).
- **Accès distant en lecture seule** (optionnel) : d'autres postes, reliés via Tailscale, peuvent consulter et imprimer l'historique des factures sans jamais écrire dans la base — voir section 2 bis.
- **Machine de facturation offline-first** (optionnel) : un poste dédié à la facturation peut fonctionner hors ligne via un cache SQLite local et une file de synchronisation, la base + le serveur API vivant alors sur la machine du boss — voir section « Machine de facturation (offline-first) ».

### Les 3 applications

Le système est pensé comme **3 applications qui communiquent** via le serveur API central (SQLite + FastAPI, hébergé sur la machine du boss) :

1. **App Facturation** (`app/ui/`, exécutable historique `SMP.exe`) : facturation, produits, clients, proforma, historique, archive, remises, dashboards, paiements (lecture), page API distante — l'application complète du gérant. Peut aussi fonctionner en mode « machine de facturation hors ligne » (voir plus bas).
2. **App Client / Serveur** (`app/client/`, exécutable `SMP-Client.exe`) : consultation à distance de l'historique, paiements (versements), vue client, dashboard, remises — et peut elle-même héberger le serveur API (onglet « Serveur ») si ce poste doit être celui qui garde la base active en continu, sans avoir besoin d'installer l'app Facturation.
3. **App Stock** (`app/stock/`, exécutable `SMP-Stock.exe`, entièrement nouvelle) : rôle unique et volontairement restreint — visibilité du catalogue et de la quantité en stock de chaque article, saisie des entrées (approvisionnement) et des ajustements correctifs. Ne gère ni facturation, ni clients, ni paiements. Voir section « Gestion de stock ».

Un 4ᵉ composant, `SMP-Serveur.exe` (`app/main_server.py`), héberge le serveur API seul, sans interface, pour tourner en tâche de fond indépendamment de l'app qui l'a démarré.

Voir `docs/ANALYSE_EXCEL.md` pour l'analyse historique de l'existant Excel qui a précédé ce projet (contexte de l'entreprise d'origine — les règles métier qui en découlaient ont depuis évolué, voir section « Règles métier clés »).

### Règles d'architecture

1. Les vues Tkinter ne touchent **jamais** la base : elles passent par les services. Aucun `import sqlite3` hors de `repositories/`.
2. Les modèles sont indépendants de Tkinter et de SQLite (dataclasses pures).
3. Aucune logique métier dans les callbacks Tkinter : le callback appelle un service et affiche le résultat.
4. Tout texte visible passe par `i18n.translations.t("cle")` — jamais de chaîne UI en dur.
5. Type hints partout, docstrings en français, PEP 8.
6. Toute nouvelle fonctionnalité suit le découpage models → repositories → services → ui.
7. Montants en **FCFA entiers** (pas de flottants pour l'argent). Dates stockées ISO (`YYYY-MM-DD`), affichées `JJ/MM/AAAA`.

## 2 bis. Produits et clients (référentiels)

### Produits — catalogue à plat (`app/models/produit.py`)

Un produit est identifié par :
- **`nom`** : nom de l'article (ex. « BIDON »).
- **`type_option`** : `'dimension'` | `'litrage'` | `''` (article sans option).
- **`valeur_option`** : la valeur du choix pour ce type d'option (ex. « 5L », « 40x60 »).
- **`prix`** : prix FCFA de **cette combinaison précise** nom + option.

Il n'y a **pas** de modèle parent/variantes : chaque combinaison `(nom, type_option, valeur_option)` est une ligne de catalogue indépendante, avec son propre prix — deux lignes « BIDON / litrage / 1L » et « BIDON / litrage / 5L » sont deux produits distincts au même titre que deux articles sans rapport. `Produit.designation` (`f"{nom} {valeur_option}"`) est le libellé utilisé partout (facturation, recherche, PDF). Unicité en base : `UNIQUE (nom, type_option, valeur_option)` (`ProduitRepository`).

**La création d'un nouvel article se fait exclusivement depuis l'app Stock** (`StockService.creer_produit`, `POST /stock/produits`, rôle `role_stock` — voir « Gestion de stock ») : la page Produits de l'app Facturation (`produits_view.py`) ne propose plus que la **modification** (nom/option/prix d'un produit déjà sélectionné) et la **fusion** de deux fiches doublons (`ProduitRepository.fusionner`, réattribue les lignes de vente puis supprime le doublon) — plus aucun bouton de création, ni sur la machine boss ni sur la machine de facturation hors ligne (`ApplicationFacturation` réutilise la même vue). Elle affiche aussi, en lecture seule, la **quantité vendue** de chaque article (`StatsService.quantite_vendue_par_produit`, total toutes ventes non archivées confondues, sans filtre de période) à côté de la quantité en stock.

### Clients (`app/models/client.py`)

Un client est identifié par :
- **`nom`** : prénom et nom.
- **`adresse`**.
- **`telephone`**.

**Le téléphone et l'adresse sont les éléments essentiels d'identification d'un client** (et non le nom seul, qui peut se répéter) : en base, `UNIQUE (nom, adresse)` autorise des homonymes à des adresses différentes, et un index unique partiel garantit qu'**un même numéro de téléphone, quand il est renseigné, n'appartient jamais qu'à un seul client** (`CREATE UNIQUE INDEX ... ON clients(telephone) WHERE telephone != ''`). `ClientRepository.obtenir_ou_creer(nom, telephone="", adresse="")` : si un téléphone est fourni et correspond à une fiche existante, elle est réutilisée en priorité (signal le plus fiable) ; sinon la correspondance se fait par (nom, adresse), avec complétion de l'adresse d'un homonyme qui n'en avait pas encore, sans jamais fusionner deux personnes différentes de même nom.

- **Normalisation du téléphone (`ClientRepository.normaliser_telephone`)** : ne garde que les chiffres (espaces, tirets, points supprimés) — deux saisies du même numéro avec un formatage différent sont ainsi reconnues comme identiques par la contrainte d'unicité et par toute recherche exacte (`chercher_par_telephone`). Ne s'applique qu'aux **nouvelles** écritures (création/modification) — les numéros déjà stockés avant ce changement gardent leur formatage d'origine, aucun nettoyage rétroactif n'a été fait.
- **Fusion automatique par téléphone (`ClientMaintenanceService.fusionner_doublon_telephone`)** : avant d'enregistrer la modification d'un client, si le nouveau téléphone correspond déjà à un **autre** client existant, ce dernier est fusionné dans la fiche en cours d'édition (qui survit, avec les valeurs tout juste saisies) via le mécanisme de fusion existant (`fusionner`, réattribution factures/remises puis suppression du doublon) — plutôt que de heurter l'index unique. Appelé par `ClientsView._enregistrer()` avant `repository.modifier()`, et côté serveur par `SyncReceptionService._rejouer_modification_client` avant d'appliquer une modification reçue d'une machine de facturation. La création (`ClientsView`) passe par `obtenir_ou_creer` pour la même raison (réutilise plutôt que de dupliquer).

**Seuls le nom et l'adresse figurent sur une facture** (jamais le téléphone) — c'est aussi le comportement du bordereau de livraison.

**Il n'y a pas de notion de sous-client/revendeur.** La page Clients ne propose qu'une seule action avancée : **Fusionner** (deux fiches doublons — typo d'adresse, saisie en double — sont réunies : factures et remises du doublon transférés puis fiche supprimée, `ClientMaintenanceService.fusionner`). Aucune hiérarchie parent/enfant, aucune dissociation de fiche, aucun export/import Excel de relations : ces fonctionnalités, propres à un modèle de vente en gros/revente qui ne s'applique pas à cette entreprise, ont été retirées.

## 2 ter. TVA obligatoire

**La TVA à 18 % s'applique automatiquement à toute facture**, sans case à cocher ni champ modifiable dans l'interface : `Facture.tva_taux` est toujours fixé par `FacturationService` à `config.TVA_TAUX_DEFAUT` (18.0) au moment de l'enregistrement, jamais saisi par l'utilisateur. Elle est **prélevée SUR le total net** (après remise éventuelle), jamais ajoutée en plus : le montant réellement dû par le client (`Facture.total_net` / `total_ttc`, identiques) ne change jamais selon la présence de la TVA — seule sa décomposition HT/TVA affichée sur le PDF en dépend (`total_ht`, `tva_montant`). **Un brouillon (proforma) affiche désormais le même détail HT/TVA/TTC qu'une facture réelle** : `Proforma.tva_taux`/`tva_montant`/`total_ht`/`total_ttc` sont des propriétés calculées dynamiquement (jamais stockées — un brouillon n'est jamais figé, contrairement à `Facture.tva_taux`) à partir de `config.TVA_TAUX_DEFAUT`, avec les mêmes formules ; `PdfService._total()` fonctionne par duck-typing sur ces quatre attributs et n'a donc pas eu besoin d'être modifié pour afficher ce détail sur le PDF proforma.

### Téléphone et matricule

Sous les lignes Client/Destination de l'en-tête PDF (facture, bordereau **et** proforma — `PdfService._entete()`, méthode partagée par les trois documents) : une ligne **Téléphone** (toujours affichée, même vide, comme Destination) et, seulement si renseignée, une ligne **Matricule**.

- **`Facture.telephone`/`Proforma.telephone`** : téléphone du client, dénormalisé sur la facture/le brouillon comme `client_nom`/`destination` (pas une simple lecture de `Client.telephone` au moment de l'impression — la valeur imprimée est celle saisie sur CETTE facture, éventuellement corrigée). `FacturationView._choisir_client` le préremplit depuis la fiche client choisie (même garde que pour `destination` : jamais écrasé si déjà saisi pour cette facture).
- **`Facture.matricule`/`Proforma.matricule`** : matricule du véhicule assurant la livraison, saisi librement dans l'en-tête de la vue Facturation (jamais préempli — propre à chaque livraison, un même client pouvant être livré par des véhicules différents d'une facture à l'autre).
- Persistés en base (`factures.telephone`/`matricule`, `proformas.telephone`/`matricule`) et propagés à travers toute la chaîne existante (`FacturationService.enregistrer_facture`/`modifier_facture`, `ProformaService.enregistrer`/`modifier`/`valider` — un brouillon validé transmet son téléphone/matricule à la facture créée), y compris la synchronisation de la machine de facturation (`app/sync/payloads.py.construire_payload_facture`/`parser_payload_facture`).

### Mention légale et cachet/signature

En bas de toute facture/proforma (jamais sur le bordereau, qui n'affiche aucun prix ni total) : la mention « *Cette présente facture est arrêtée à la somme de : [montant en toutes lettres] francs CFA.* » (`PdfService._mention_montant_lettres`, montant = `total_ttc`, converti par `app/utils/nombre_lettres.nombre_en_lettres_fr` — implémentation autonome, aucune dépendance externe type `num2words`) puis, juste en dessous, le libellé « **Cachet et signature** » en gras souligné, **sans cadre** (`PdfService._bloc_signature`) — volontairement pas de rectangle : l'espace sous ce libellé doit rester totalement libre pour un cachet circulaire d'environ **10 cm de diamètre** (`_DIAMETRE_CACHET`).

Total → mention → libellé cachet/signature s'enchaînent **directement à la suite les uns des autres** (chacun retourne le `y` où continuer le suivant), plutôt que d'ancrer la mention/le cachet à une position fixe indépendante du total : sans cet enchaînement, un total positionné juste après un tableau court et une mention/un cachet ancrés en bas de page laisseraient un grand vide entre les deux. Ce bloc reste **toujours sur la même page que le tableau** — volontairement **aucun saut de page forcé** ne lui est dédié (contrairement à une version antérieure de cette fonctionnalité qui en imposait un dès que les ~162mm nécessaires au pire cas, remise+TVA+cachet, n'étaient pas disponibles) : sur une facture à beaucoup de lignes remplissant presque toute la page, ce bloc peut donc se retrouver serré contre la marge basse, voire légèrement au-delà — accepté en échange de ne jamais scinder une facture usuelle (la grande majorité, avec peu de lignes) sur deux pages pour cette seule raison.

## 2 quater. Gestion de stock

Fonctionnalité entièrement nouvelle (absente du projet d'origine) : suivi de la quantité en stock de chaque article du catalogue, décrémentée automatiquement à la vente, alimentée manuellement (entrées/ajustements) depuis une application dédiée.

- **`produits.quantite_stock`** : quantité en stock courante, mise en cache sur chaque ligne du catalogue (un produit = un SKU vendable, cohérent avec le catalogue à plat — voir « Produits »). Gérée **exclusivement** par les mouvements de stock ci-dessous — jamais modifiée par une simple édition du catalogue (`ProduitRepository.modifier` ne touche pas cette colonne).
- **`mouvements_stock`** (append-only, même esprit que `versements`) : journal de tous les mouvements — `produit_id`, `type_mouvement` (`'entree'` | `'sortie'` | `'ajustement'`), `quantite` (**delta signé** : positif pour une entrée, négatif pour une sortie ou un ajustement correctif), `reference` (numéro de facture pour une sortie liée à une vente, note libre pour une entrée/ajustement manuel), `source` (`'vente'` | `'manuel'`), `machine_id`, `cree_le`. Aucune méthode `modifier`/`supprimer` — une correction s'effectue par un nouveau mouvement compensatoire.
- **Décrément automatique à la facturation** (`FactureRepository.enregistrer`/`modifier`, appelées par `FacturationService`) : pour chaque ligne vendue rattachée à un produit, une sortie (`quantite` négative, `source='vente'`, `reference=str(facture_id)`) est enregistrée et `produits.quantite_stock` décrémenté **dans la même transaction SQL** que l'écriture de la facture — jamais de facture sans son mouvement de stock, ni l'inverse. Modifier une facture existante **annule d'abord** (mouvement `'ajustement'` compensatoire, jamais une suppression — le journal reste append-only) les sorties de l'ancienne version avant d'appliquer celles des nouvelles lignes (`FactureRepository._reverser_sorties_stock`/`_appliquer_sorties_stock`). **Supprimer** une facture (`FactureRepository.supprimer`, `FacturationService.supprimer_facture`) restitue le stock de la même façon (appelle `_reverser_sorties_stock` avant le `DELETE`) — un retour, comme si les articles n'avaient jamais quitté le stock.
- **Blocage à l'ajout au panier (`FacturationView._ajouter_ligne`)** : toute ligne doit correspondre à un produit déjà existant du catalogue — `_resoudre_produit_id` retrouve son id par désignation exacte (insensible à la casse) si l'usager n'est pas passé par la liste déroulante ; sans correspondance, la ligne est refusée (message `fact_produit_inconnu`, invitant à créer le produit depuis l'app Stock). Une fois le produit résolu, `_verifier_stock_disponible` relit son stock courant (`ProduitRepository.obtenir`, lecture directe en base, pas le cache de `rafraichir()`) et refuse la ligne si `quantité déjà au panier pour ce produit + quantité de la ligne > stock disponible` (message `fact_stock_insuffisant`, indiquant la quantité restante). Ces deux contrôles sont des gardes d'interface, au moment de la saisie — ils ne remplacent pas la couche service/repository : `FacturationService._rattacher_produit` garde en interne son ancien filet de sécurité (créer le produit à la volée si aucune correspondance), utile aux tests et à un appel direct du service, mais rendu inatteignable en usage normal par le blocage de l'UI ; et rien n'empêche `quantite_stock` de devenir négatif si on contourne l'UI (import direct, synchronisation de deux machines vendant en même temps le reste d'un stock limité, ajustement manuel concurrent) — cohérent avec la philosophie générale de ne jamais bloquer une écriture déjà validée, juste signalé visuellement (rouge) dans l'app Stock le cas échéant.
- **« Stock disponible » lors de la correction d'une facture déjà enregistrée** : ce n'est pas seulement `quantite_stock`. `charger_pour_edition(facture)` calcule `_quantites_originales_facture` (quantité déjà sortie du stock, par produit, dans CETTE facture telle qu'enregistrée) ; `_verifier_stock_disponible` compare alors à `quantite_stock + _quantites_originales_facture[produit_id]`. Exemple : facture de 100 plats, stock actuel à 2 (après cette vente) — corriger cette ligne à 50 (retour de 50 articles) est comparé à `2 + 100 = 102`, jamais aux 2 seuls en stock, sans quoi toute correction à la baisse d'une facture ayant vidé le stock serait refusée à tort (`FactureRepository.modifier` restitue de toute façon puis réapplique ces sorties à l'enregistrement — voir ci-dessus). Ce crédit est propre à l'édition d'une facture réelle : remis à `{}` pour une facture neuve ou le chargement d'un brouillon (`charger_pour_edition_proforma`), qui n'ont jamais décrémenté le stock.
- **Machine de facturation hors ligne** : le cache SQLite local partage exactement le même schéma (`produits.quantite_stock`, `mouvements_stock`) que la base boss, et le décrément d'une vente faite **sur cette machine** fait partie du même code déjà rejoué par la file de synchronisation montante existante (`creation_facture`/`modification_facture`) — aucune opération de synchro dédiée n'a été nécessaire pour ce sens-là. En revanche, le stock bougé **ailleurs** (entrées/ajustements saisis via l'app Stock, ventes faites sur une autre machine) n'atteint cette machine que par la synchro **descendante** du référentiel : `ReferentielSyncWorker._synchroniser_produits` (`app/sync/referentiel_worker.py`) pousse désormais aussi `quantite_stock` vers le cache local à chaque cycle (`ProduitRepository.definir_quantite_stock`, une écriture séparée de `modifier` qui ne doit jamais toucher cette colonne pour une simple édition de catalogue) — sans quoi le blocage anti-survente de `FacturationView` comparerait indéfiniment une quantité locale figée à sa valeur de création. Fenêtre d'incohérence possible le temps d'un cycle (`intervalle_referentiels_secondes`, 300 s par défaut) entre deux machines vendant le même article : cohérent avec la philosophie générale de l'app (cohérence à terme, jamais de blocage bloquant sur l'écriture elle-même).
- **`app/repositories/stock_repository.py` (`StockRepository`)** : écritures manuelles (`enregistrer_mouvement`), `historique(produit_id)`, `stock_actuel(produit_id)`.
- **`app/services/stock_service.py` (`StockService`)** : `lister_produits()`, `creer_produit(nom, type_option="", valeur_option="", prix=0)` (stock initial à 0, lève `ErreurValidation("prod_existe")` en cas de doublon), `modifier_produit(produit_id, nom, type_option="", valeur_option="")` (jamais le prix ni le stock), `supprimer_produit(produit_id)` (refuse proprement — `ErreurValidation("stock_produit_utilise")` — si le produit est encore référencé par des lignes de vente, plutôt que de laisser remonter la `sqlite3.IntegrityError`), `entrer_stock(produit_id, quantite, note="", machine_id="")` (quantité strictement positive), `ajuster_stock(produit_id, delta, motif="", machine_id="")` (delta signé, non nul), `historique(produit_id)`, `stock_actuel(produit_id)`. **Seul point de création** d'un nouvel article de catalogue ; la modification nom/option y est également possible (`modifier_produit`), mais le **prix** reste un réglage exclusif de l'app Facturation, et la **fusion** de doublons reste sa seule prérogative (`ProduitRepository`, page Produits) — `produits_view.py._supprimer` attrape désormais la même `sqlite3.IntegrityError` (bug préexistant : une suppression avec ventes liées faisait planter l'app).
- **API** (`app/api/routes_stock.py`, préfixe `/stock`, réservé au rôle `role_stock`) :
  - `GET /stock/produits` — catalogue + quantité en stock de chaque article.
  - `POST /stock/produits` (`{nom, type_option, valeur_option, prix}`) — crée un nouvel article (stock initial à 0). `prix` est accepté par l'API pour rester compatible avec `StockService.creer_produit`, mais l'app Stock ne l'expose **jamais** dans son dialogue (toujours envoyé à 0) : le prix reste un réglage exclusif de l'app Facturation, à corriger depuis sa page Produits juste après la création. Même file FIFO que les écritures ci-dessous.
  - `PUT /stock/produits/{id}` (`{nom, type_option, valeur_option}`, jamais de prix) — modifie un article existant.
  - `DELETE /stock/produits/{id}` — supprime un article ; 400 s'il est encore référencé par des ventes déjà enregistrées.
  - `POST /stock/produits/{id}/entree` (`{quantite, note}`) — enregistre une entrée. Passe par la file FIFO d'écriture (`app/api/write_queue.py`, même mécanisme que les versements — chaque tâche ouvre sa propre connexion SQLite dans le thread worker).
  - `POST /stock/produits/{id}/ajustement` (`{delta, motif}`) — enregistre un ajustement correctif, même sérialisation FIFO.
  - `GET /stock/produits/{id}/historique` — mouvements d'un produit, les plus récents d'abord.
- **App Stock** (`app/stock/`, `SMP-Stock.exe`, `python -m app.main_stock`) : fenêtre Tkinter unique et volontairement minimale — table du catalogue **sans jamais afficher le prix** (nom/option/valeur/quantité seulement — le prix reste un réglage exclusif de l'app Facturation, même en lecture ici), quantité en stock (lignes en négatif signalées en rouge), recherche live, bouton **« Nouveau produit »** (dialogue nom/option/valeur, sans champ prix — seule voie de création du catalogue, voir ci-dessus), boutons **« Modifier le produit »** (même dialogue pré-rempli, nom/option seulement) et **« Supprimer le produit »** (confirmation puis `DELETE`, message clair si le produit est encore référencé par des ventes plutôt qu'une erreur brute), boutons « Entrée de stock » et « Ajustement » (dialogues dédiés), panneau d'historique des mouvements par produit, configuration de connexion (hôte/port/jeton `role_stock`/identifiant machine, persistée dans `stock_config.json`), rafraîchissement automatique du catalogue toutes les 15 secondes (`ApplicationStock._auto_actualiser`, silencieux, en plus du bouton « Actualiser » — la sélection courante est préservée à travers ces rafraîchissements). Client HTTP pur (`requests` uniquement) — pas de SQLite, pas de matplotlib, pas de reportlab, pas de fastapi/uvicorn embarqués : c'est le plus léger des exécutables du projet.
- **App Stock — mode hors ligne (option de secours)** : cache local léger + file d'attente locale, sur le modèle déjà existant d'`app/client/queue_hors_ligne.py` pour les versements — **pas** une réplique de l'architecture offline-first de la machine de facturation (SQLite + workers, voir « Machine de facturation ») : ce choix, plus lourd, aurait changé la philosophie volontairement minimale de cette app (ci-dessus) pour un besoin réel plus restreint que celui de la facturation.
  - **`app/stock/cache_catalogue.py`** : à chaque `actualiser()` réussi, la dernière réponse de `GET /stock/produits` est écrasée dans un fichier JSON (`stock_catalogue_cache.json`, à côté de `stock_config.json`), horodatée. `ApplicationStock._basculer_sur_cache()` : si le serveur devient injoignable (`ErreurInjoignable` — pas un jeton refusé ni une autre erreur applicative, qui restent affichées telles quelles, aucune bascule silencieuse), le catalogue en cache est utilisé pour peupler le tableau, avec un statut « Hors ligne — catalogue en cache (dernière synchro : HH:MM) » plutôt que le message d'erreur brut.
  - **`app/stock/queue_hors_ligne.py`** : si une entrée ou un ajustement échoue avec `ErreurInjoignable`, `ApplicationStock._proposer_mise_en_attente` propose (comme `app/client/ui.py._ajouter_versement` pour un versement) de l'enregistrer localement (`OperationStockEnAttente` : `type_operation`, `produit_id`, `quantite` — delta signé, réutilise directement la sémantique déjà validée côté API — `note`, `date_saisie`). Le `produit_id` référencé est toujours celui du catalogue en cache, donc déjà connu du serveur : aucun problème de corrélation d'id local ↔ serveur (contrairement à une création de produit).
  - **Volontairement exclu** : création/modification/suppression de produit hors ligne — nécessiterait cette corrélation d'id, la source de complexité qui a justifié toute l'architecture SQLite + workers de la machine de facturation. Ces actions restent réservées à une connexion active, comme aujourd'hui.
  - **Rejeu** : `ApplicationStock._renvoyer_operations_en_attente` rejoue la file dans l'ordre — automatiquement et silencieusement à chaque `actualiser()` réussi (donc aussi lors du cycle auto de 15 s), et à la demande via le bouton « 🔄 Renvoyer (N) » de la barre d'actions (affiche alors un résumé `X / Y synchronisées`). Une opération qui échoue encore reste en file pour le prochain passage ; celles qui réussissent sont retirées et le catalogue est immédiatement rechargé pour refléter les quantités à jour.
- **4ᵉ rôle API `role_stock`** (`config.ROLES_API`, jeton `api_token_stock` / `PROMATELAS_API_TOKEN_STOCK`) : n'a accès **qu'** aux endpoints `/stock/*` — jamais à l'historique des factures, aux paiements, ni aux référentiels de synchronisation. Généré depuis la page « API distante » de l'app Facturation (`api_view.py`, 4ᵉ champ de jeton) ou depuis l'onglet « Serveur » de l'app Client (`OngletServeur`, 4ᵉ ligne), au même titre que les 3 autres rôles.

## 3. Accès distant (`app/api/` + `app/client/`)

- **But** : consulter et imprimer l'historique des factures depuis un autre poste (relié par Tailscale/ZeroTier à la machine principale), y enregistrer des **versements** et appliquer des **remises**, et — via l'app Stock — consulter/mettre à jour le stock. Tout reste local (SQLite) — aucune migration vers un serveur distant, aucun VPS.
- **Périmètre exposé** (`/factures`, `/factures/{id}`, PDF, bordereau) : l'historique complet des factures, non archivées par défaut. `app/api/routes.py` reste 100 % lecture seule (n'a que des `GET`) — les écritures vivent dans `routes_paiements.py` et `routes_stock.py`.
- **Permissions par ressource**, quatre rôles, chacun avec son propre jeton statique :

  | Ressource | `role_client` | `role_principal` | `role_facturation` | `role_stock` |
  |---|---|---|---|---|
  | Factures (lecture, PDF, bordereau) | ✅ | ✅ | ❌ | ❌ |
  | Recherche clients (nom/adresse/téléphone, lecture seule) | ✅ | ✅ | ❌ | ❌ |
  | Versements — écriture | ✅ | ❌ (403) | ❌ | ❌ |
  | Versements — lecture | ✅ | ✅ | ❌ | ❌ |
  | Remise par facture — écriture | ❌ (403) | ✅ | ❌ | ❌ |
  | Remise annuelle — écriture | ✅ | ✅ | ❌ | ❌ |
  | Totaux/synthèse paiements | ✅ | ✅ | ❌ | ❌ |
  | Réservation de numéros / rejeu d'opérations / référentiels / historique complet / archive | ❌ | ❌ | ✅ | ❌ |
  | Catalogue + stock (lecture), création de produits + entrées/ajustements (écriture) | ❌ | ❌ | ❌ | ✅ |

  L'app **client** utilise le jeton `role_client`. La remise **par facture** reste réservée à `role_principal` — c'est l'app Facturation qui écrit les factures, donc leur remise ponctuelle. L'app **Facturation** n'a besoin d'aucun jeton pour ses propres pages locales : elle accède directement à ses services sur sa connexion SQLite, sans passer par l'API.
- **Couche `api/`** : les routeurs FastAPI appellent uniquement les services — jamais un repository directement. Chaque requête ouvre sa **propre connexion SQLite** (`app/api/deps.py`) : mode **WAL** (`PRAGMA journal_mode=WAL`) pour que les lectures continuent pendant une écriture.
- **Authentification par rôle** (`app/api/auth.py`) : `identifier()` compare le jeton reçu (`X-API-Key`) à temps constant contre chacun des quatre jetons configurés (`config.lire_api_token(role)`) — écrit génériquement sur `config.ROLES_API`, un futur rôle n'exige donc aucune modification de `auth.py`. `exiger_role(*roles)` est une fabrique de dépendance pour un contrôle par route.
- **Écoute réseau** : `api_host` par défaut à `127.0.0.1` (jamais exposée tant que l'utilisateur n'a pas réglé l'hôte sur l'IP Tailscale, ex. `100.x.y.z`).
- **Serveur autonome** : tourne dans un **processus séparé** de la fenêtre Tkinter (`app/main_server.py` → `app.api.server.demarrer()` → `uvicorn.run(app, ...)`, packagé en `SMP-Serveur.exe`) — continue de tourner après la fermeture de l'app qui l'a démarré. `ApiManagementService` pilote ce processus (démarrage/arrêt/démarrage auto avec Windows via le dossier de démarrage utilisateur, jamais le Planificateur de tâches).
- **Page « API distante »** (`app/ui/views/api_view.py`) : configuration hôte/port + **quatre** champs de jeton (client/principal/facturation/stock, chacun avec son bouton « Générer »), statut en ligne/arrêté, Démarrer/Arrêter, démarrage automatique.
- **Mode client** (`app/main_client.py` → `app/client/ui.py`) : fenêtre Tkinter à **sept onglets** — Historique/Impression, Paiements, Vue client, Dashboard, Remises, **Import historique** (voir plus bas), **Serveur** (pilotage de `SMP-Serveur.exe` directement depuis ce poste, avec ses quatre jetons — pertinent quand ce poste héberge la base). Coordonnées de connexion persistées dans `client_config.json`. Recherche client : nom, adresse ou téléphone (`ClientRepository.rechercher`).
- **Internationalisation du mode client** : fr/中文 uniquement (`_LANGUES_CLIENT`), langue persistée dans `client_config.json` (jamais `settings.json`, propre à l'app Facturation).
- **Client multiplateforme (Windows + macOS)** : le mode client tourne aussi sur Mac (`build_client_mac.sh`) ; le reste du projet (y compris l'app Stock) est Windows uniquement.
- **Auto-connexion à son propre serveur** : quand un poste héberge lui-même la base (jeton `role_client` local déjà généré via l'onglet Serveur), l'app Client se connecte automatiquement à `127.0.0.1` via `AccesDirectDonnees` (lectures directes SQLite, écritures toujours via HTTP interne pour rester sérialisées par la file FIFO du serveur) plutôt que par une saisie manuelle — sauf si une connexion manuelle distante a déjà été enregistrée, qui reste toujours prioritaire.

## Paiements (versements) — `app/models/versement.py`, `app/repositories/versement_repository.py`, `app/services/paiement_service.py`

- **But** : suivre le solde de chaque facture (montant dû après remise, versé, restant) au fil des versements reçus, saisis depuis un poste distant (`role_client`) — l'app Facturation n'a qu'une vue de consultation (page « Paiements », lecture seule) plus une page « Vue client » (synthèse par client).
- **Append-only strict** (`versements`) : aucune méthode `modifier`/`supprimer` — une correction s'effectue via un **versement négatif** compensatoire. `montant` peut être négatif ; seul `0` est refusé.
- **Solde** : `PaiementService.calculer_solde_facture` calcule `total` (= `Facture.total_net`, qui inclut la TVA prélevée dessus — jamais un supplément), `verse`, `restant`. Le trop-perçu (`restant < 0`) est autorisé librement.
- **Remises tracées** : `Facture.remise_modifiee_par`/`remise_modifiee_le` (remise par facture, `role_principal` uniquement) et `Remise.modifie_par`/`modifie_le` (remise annuelle, écrite par les deux rôles distants, en pratique surtout l'app cliente — voir « Vue client »).
- **Téléphone affiché et recherché** : `Facture.telephone` (dénormalisé, voir « Téléphone et matricule ») est exposé en colonne dans l'historique des factures, Paiements et Vue client (App Client `app/client/ui.py` — `OngletHistorique`/`OngletPaiements`/`OngletVueClient` — et leurs équivalents locaux de l'app principale, `paiements_view.py`/`vue_client_view.py`, ainsi que « Historique complet », qui réutilise `OngletHistorique` tel quel via `historique_view_distant.py`). La recherche de factures (`PaiementService.lister_avec_solde`, page Paiements) matche aussi ce téléphone, en plus du nom client/destination/numéro ; l'historique (recherche entièrement côté client) a son propre champ dédié « Téléphone ». La recherche de **clients** (`ClientRepository.rechercher`, utilisée par Vue client) matchait déjà le téléphone, sans changement nécessaire.
- **File d'attente FIFO des écritures** (`app/api/write_queue.py`) : sérialise `POST /paiements/facture/{id}/versement` et les écritures de stock (`POST /stock/produits/{id}/entree`/`ajustement`) — un worker unique, chaque tâche ouvre sa propre connexion SQLite dans le thread worker.
- **Résilience réseau côté client** (`app/client/queue_hors_ligne.py`) : si l'API est injoignable à la saisie d'un versement, l'UI propose de le stocker dans une file JSON locale, rejouable au retour de connexion. Jamais utilisée pour calculer un solde affiché.

### Import des paiements historiques (App Client)

**But** : réimporter au moins le suivi de règlement des anciennes factures (avant ce système) pour chaque client, sans avoir à réimporter les factures elles-mêmes — le fichier source de l'ancien système ne conserve pas les factures sous une forme exploitable (un ensemble de documents, pas une liste), contrairement à un simple résumé de paiements (date, numéro, client, montant, versement, solde, commentaire), une ligne par ancienne facture. Onglet **« Import historique »** de l'app Client, `app/client/ui.py::OngletImportLegacy`.

- **Format du fichier source** : les en-têtes/le texte peuvent être en chinois — jamais lus par nom, toujours par **position** (colonnes/lignes), voir `app/client/ui.py::analyser_feuille_import_legacy`. 3 lignes sautées, en-tête à la ligne 4, données à partir de la ligne 5. Colonnes (0-indexées) : 0 date, 1 numéro facture, 2 client (nom + numéro concaténés, une seule chaîne, jamais découpée — aucun séparateur fiable connu), 3-5 vides, 6 montant (colonne 7 du fichier), 7 montant dupliqué (colonne 8, repli si la colonne 7 est vide ; écart entre les deux signalé en avertissement mais n'empêche pas l'import), 8 versement, 9 solde (jamais stocké tel quel — sert uniquement à un contrôle de cohérence optionnel), 10 commentaire. Lecture entièrement côté App Client (`openpyxl`, déjà une dépendance embarquée dans `SMP-Client.exe` via `app/utils/export_paiements_excel.py` — `SMP-Serveur.exe` n'en a pas besoin) : le fichier brut ne transite jamais sur le réseau, seules les lignes déjà validées (numéro/date/montant numériques) sont envoyées, en un seul appel.
- **Facture « coquille »** : chaque ligne valide crée une `Facture` dont le **numéro est celui de l'ancien système, tel quel** (reconnaissable dans l'historique), avec une seule `LigneVente` synthétique (« Import historique », quantité 1, prix = montant) portant le montant total, `remise_taux=0`, **`tva_taux=0`** (jamais réappliquer la TVA courante à un montant historique dont le traitement fiscal d'origine est inconnu). Écrite directement via `FactureRepository.enregistrer(facture, ventes_stock=None)` — **jamais** via `FacturationService`, qui auto-créerait un faux article au catalogue et déclencherait une sortie de stock fictive à chaque ligne importée. `app/services/import_paiements_legacy_service.py::ImporterPaiementsLegacyService`.
- **Numérotation** : le numéro importé est utilisé tel quel, sans exiger qu'il soit inférieur au plus grand numéro de facture réelle déjà utilisé — **bug corrigé** : une première version de cet import rejetait à tort des lignes historiques légitimes sous ce prétexte, alors qu'en pratique la numérotation de l'ancien système et celle de ce système démarrent souvent chacune à des petits nombres proches, donc les deux plages se chevauchent normalement. Seule l'**unicité** est exigée (contrainte `UNIQUE` déjà en base, `idx_factures_numero_unique`) : une ligne dont le numéro est déjà utilisé par une autre facture (réelle ou déjà importée) est **ignorée et reportée** (`numero_deja_utilise`), sans jamais interrompre le reste du lot — cohérent avec le reste de l'application, où la numérotation reste « auto-incrémentée mais modifiable » (voir section 1), jamais un invariant strict de continuité sans trou.
- **Versement** : si la colonne « versement » est non nulle, un `Versement` est créé (`role_origine="import_legacy"`, distinct des rôles API réels, pour tracer ces écritures) via `PaiementService.enregistrer_versement` (mêmes validations qu'un versement normal — `montant == 0` refusé, donc pas de versement créé si la colonne est vide/nulle : la facture reste simplement impayée).
- **Permission API** : `POST /paiements/import-legacy` réutilise le rôle `role_client` existant (déjà autorisé en écriture sur les paiements) — pas de nouveau rôle/jeton. Traite tout le lot en une seule tâche de la file FIFO (`app/api/write_queue.py`) plutôt qu'un appel par ligne — acceptable, outil de migration ponctuelle et non une opération fréquente.
- **Client** : résolu/créé via `ClientRepository.obtenir_ou_creer(nom=<colonne client>, adresse="")` — la chaîne concaténée brute sert de nom. Risque assumé : des variantes mineures de la même chaîne créent des fiches distinctes, corrigible ensuite via la fusion de fiches déjà existante (page Clients).

## Machine de facturation (offline-first) — `app/sync/`, `app/ui/app_facturation.py`, `app/api/routes_sync.py`

- **But** : la base SQLite + le serveur API vivent sur la machine du **boss** (allumée en continu) — elle reste l'unique source de vérité. La machine qui **facture** (souvent éteinte/intermittente) est cliente en écriture, mais reste **pleinement fonctionnelle hors ligne** : créer une facture, l'imprimer, consulter son historique local, gérer produits/clients — puis se réconcilier automatiquement dès que le réseau revient. Cache SQLite local (`config.CHEMIN_CACHE_FACTURATION`, **même schéma** que la base boss) + file de synchronisation typée, traitée dans l'ordre.
- **Périmètre UI** (`ApplicationFacturation`) : Facturation, Proforma, Historique (local), Produits, Clients, plus un bandeau de statut de synchro. **Dashboards, Remises, Archive, Paiements et la page API restent réservés à la machine boss.**
- **Troisième rôle API `role_facturation`** : n'a accès qu'aux endpoints de synchronisation (`app/api/routes_sync.py`) et d'administration réseau (`app/api/routes_admin.py`) — jamais aux paiements ni au stock.
- **Numérotation résiliente** (jamais de numéro généré ad hoc sans garantie d'unicité) — voir section dédiée ci-dessous, « Numérotation résiliente ».
- **`NumeroReservationWorker`**, **`ArchiveStatutSyncWorker`**, **`ReferentielSyncWorker`**, **`SyncWorker`** : quatre threads daemon indépendants (alimentation du pool de secours de numéros, synchronisation du statut d'archivage, pull descendant du référentiel produits/clients, file montante des créations/modifications) — voir le code de chacun pour le détail, inchangé dans son principe depuis la conception initiale, seulement adapté aux nouveaux modèles Produit/Client (`nom`/`type_option`/`valeur_option`/`prix` ; `nom`/`telephone`/`adresse`, sans résolution de parent).
- **Un thread daemon ne doit jamais mourir sur une exception imprévue** (bug corrigé) : chaque `_boucle()` enveloppe désormais son appel de cycle (`synchroniser()`/`_traiter_file()`) dans un `try/except Exception` dédié, en plus de la gestion déjà spécifique à chaque worker (`ErreurApiSync` et ses sous-classes) — sans ce filet, une erreur non prévue (ex. verrou SQLite concurrent, voir ci-dessous) tuait silencieusement le thread pour le reste de la session : en exécutable `--windowed` (sans console), la trace n'était visible nulle part, et toute synchro (montante ou descendante selon le worker touché) s'arrêtait alors pour de bon jusqu'au redémarrage de l'app — symptôme observé : synchronisation « lente, voire ça ne passe pas du tout » pour certaines opérations (créations de produit/entrées de stock via l'app Stock) quand la vente, elle, semblait toujours instantanée (déclenchée immédiatement via `notifier_immediat`, moins exposée).
- **`PRAGMA busy_timeout = 5000`** (`creer_connexion`, `app/repositories/base_repository.py`) : sans ce réglage (délai par défaut de SQLite = 0 ms), la moindre écriture concurrente entre les threads UI et workers — chacun avec sa propre connexion vers le même fichier cache — levait immédiatement `database is locked` plutôt que d'attendre que l'autre connexion termine sa transaction ; combiné au point précédent, c'était la cause probable des synchronisations qui « ne passaient pas » de façon intermittente.
- **Synchro montante quasi immédiate, pas seulement périodique** : `QueueSyncRepository.notifier_immediat()` (appelée juste après le commit réel de l'opération — jamais depuis `enfiler_sans_commit`, dont la transaction n'est pas encore visible pour le `SyncWorker`, qui lit sur une connexion séparée) réveille aussitôt `SyncWorker.declencher_immediat()`, câblé une fois pour toutes à la construction de `ApplicationFacturation` (`on_enfiler=lambda: self.sync_worker.declencher_immediat()` — un lambda plutôt qu'une référence directe, pour rester valide après le remplacement de `self.sync_worker` par `_ouvrir_config()`). Concerne toute opération enfilée (`creation_facture`/`modification_facture` via `FactureRepository`, `creation_client`, `creation_produit`, `fusion_client`) : dès qu'une facture est enregistrée, un client créé, etc., la tentative de synchro part immédiatement si le réseau est disponible, sans attendre `intervalle_sync_secondes` (120 s, qui ne sert plus que de filet de rattrapage — ex. reprise après une coupure réseau sans nouvelle écriture locale entre-temps).
- **Descente des changements du boss (prix, stock, nouveaux produits) accélérée, mais toujours en polling** : aucun canal de notification push n'existe côté serveur — `ReferentielSyncWorker` reste un pull périodique, mais son intervalle par défaut (`intervalle_referentiels_secondes`) est passé de 300 s à **20 s**, pour que le cache d'une machine de facturation hors ligne reste proche du boss en pratique. Un vrai push (WebSocket/SSE) rendrait la propagation réellement instantanée mais n'a pas été retenu (ajout d'architecture significatif — connexions persistantes, reconnexion) pour un gain marginal par rapport à 20 s.
- **Bug corrigé — un produit renommé depuis l'app Stock se dupliquait au lieu d'être mis à jour** : `ReferentielSyncWorker._synchroniser_produits` retrouvait chaque produit par sa clé naturelle (nom, type_option, valeur_option) — un renommage (`PUT /stock/produits/{id}`) rendait donc l'ancien nom introuvable localement au cycle suivant, créant un doublon plutôt que de mettre à jour l'existant. Corrigé par `produits.id_serveur` (colonne ajoutée au schéma canonique, migrée pour les bases existantes via `_migrer`, désormais appelée pour les deux moteurs) : l'id du produit **côté boss**, appris et adopté sur la ligne locale dès qu'une correspondance est trouvée (par `id_serveur` en priorité, sinon par clé naturelle en repli — cas d'un produit jamais encore lié) ; `ProduitRepository.chercher_par_id_serveur` sert cette recherche prioritaire, et `modifier()` persiste désormais aussi nom/type_option/valeur_option (pas seulement prix/actif comme avant ce correctif). Convergence automatique en un seul cycle après la mise à jour : le premier pull relie chaque produit existant à son `id_serveur` via la clé naturelle (encore valide à ce moment précis), rendant tout renommage **ultérieur** correctement détectable.
- **Suppressions non synchronisées, par choix** : supprimer un client ou un produit reste un effet **purement local** à la machine où l'action est faite (`ClientRepository.supprimer`/`ProduitRepository.supprimer`, hérités tels quels par les variantes hors ligne, jamais enfilés) — aucun type d'opération `suppression_client`/`suppression_produit` n'existe dans la file de synchro. Choix délibéré (V1) pour éviter les conflits (ex. supprimer un client/produit encore référencé par une facture en attente de synchro ailleurs) ; resynchroniser plus vite (ci-dessus) ne change rien à ce périmètre.
- **Corrélation client/serveur sans mapping d'ids** : le payload de la file de synchro transporte des clés naturelles (nom client texte, lignes avec désignation/prix), jamais un id local. `cle_correlation = str(numero)` (plus de préfixe de type, un seul type existant).
- **Fusion de client rejouée, conflit détecté et journalisé** (`SyncReceptionService._rejouer_fusion_client`) : le payload porte les clés naturelles (nom + adresse) des deux fiches. Conflit = le `modifie_le` actuel de l'une des deux fiches diffère de celui connu au moment de la décision. La fusion est appliquée malgré le conflit, journalisée dans `historique_fusions_clients` (colonnes `client_a_garder_adresse`/`client_a_supprimer_adresse`). Page **« Journal fusions »** (boss, lecture seule).
- **`POST /sync/operation`** (`role_facturation`) : passe par la même file FIFO que les versements/le stock. `SyncReceptionService.rejouer(type_operation, cle_correlation, payload, machine_id, cree_le)` route vers `creation_facture` | `modification_facture` | `suppression_facture` | `creation_client` | `creation_produit` | `modification_produit` | `modification_client` | `fusion_client`.
- **Suppression de facture synchronisée** (`suppression_facture`) : sans cela, le boss continuerait de voir une facture qui n'existe plus sur la machine de facturation qui l'a supprimée — donnée fausse par construction. `FacturationServiceHorsLigne.supprimer_facture` enfile l'opération (payload `{numero}`, seule clé de corrélation fiable) dans la MÊME transaction que la suppression locale et la restitution de stock (`FactureRepository.supprimer`, voir « Gestion de stock »). Réutilise volontairement la **même** `cle_correlation_facture(numero)` qu'une création/modification de cette facture : si celle-ci était encore en attente de synchro (créée puis supprimée avant d'avoir jamais atteint le serveur), la file la remplace par cette suppression plutôt que d'empiler les deux (même mécanisme déjà en place pour `modification_facture`). Côté serveur, `SyncReceptionService._rejouer_suppression_facture` retrouve la facture par son numéro et la supprime ; si elle est déjà absente (exactement le cas ci-dessus), ne fait rien — le résultat voulu est déjà atteint, ce n'est pas une erreur.
- **Modification autonome de produit/client synchronisée** (`modification_produit`/`modification_client`) : les pages Produits/Clients de la machine de facturation ne se contentent plus de modifier le cache local — `ProduitRepositoryHorsLigne.modifier`/`ClientRepositoryHorsLigne.modifier` (`app/sync/referentiels_hors_ligne.py`) enfilent aussi l'opération correspondante, sans quoi le prochain pull descendant du référentiel (`ReferentielSyncWorker`, toutes les 20 s) écraserait la modification locale avec l'ancienne valeur encore en base côté boss. Le payload porte l'identité **AVANT** modification (`ancien_nom`/`ancien_type_option`/`ancien_valeur_option` pour un produit, `ancien_nom`/`ancien_adresse` pour un client) — seule clé fiable pour retrouver la fiche côté serveur, capturée par une lecture (`self.obtenir(id)`) juste avant l'écriture locale, jamais un id local. Ces clés de corrélation (`modification_produit:...`, `modification_client:...`) utilisent un préfixe distinct de celui d'une création, pour ne jamais fusionner à tort avec une `creation_produit`/`creation_client` encore non synchronisée du même élément dans la file d'attente locale. Côté serveur, `SyncReceptionService._rejouer_modification_produit`/`_rejouer_modification_client` retrouvent la fiche par l'ancienne identité (la créent directement si introuvable, même philosophie de résilience que pour une création) ; côté client, une fusion automatique (`ClientMaintenanceService.fusionner_doublon_telephone`) absorbe le cas où le nouveau téléphone appartient déjà à une autre fiche.

### Numérotation résiliente

Remplace l'ancien schéma « pré-remplissage silencieux d'un bloc de 20 en tâche de fond », puis un schéma intermédiaire à popup de confirmation (JIT bloquant à l'ouverture de l'onglet) — **abandonné à son tour** au profit du schéma final ci-dessous : suggestion instantanée + confirmation silencieuse, jamais de popup, jamais de blocage. Trois paliers, du nominal au plus dégradé :

- **Palier 1 — suggestion instantanée + confirmation silencieuse (nominal)** : deux temps, jamais de popup.
  1. **Sondage continu en arrière-plan** : `NumeroPollerWorker` (`app/sync/numero_poller_worker.py`, thread daemon indépendant, cadence 3-5 s) interroge `GET /factures/dernier-numero` (`FacturationService.dernier_numero_connu()`, lecture pure — **sans aucun verrou**, jamais une réservation) et met à jour `etat_numerotation.base_connu`/`dernier_poll_reussi` (`EtatNumerotationRepository.marquer_poll_reussi`) à chaque sondage réussi.
  2. **Ouverture d'un panier neuf** (`FacturationView.rafraichir`/`_reinitialiser_panier`, jamais redéclenché tant qu'un numéro reste affecté au panier, y compris en changeant d'onglet, ni en mode édition d'une facture/d'un brouillon existant) : `_definir_numero_suggere()` affecte immédiatement, **sans réseau et sans popup**, `NumeroResilientService.suggerer_numero()` — `base_connu + 1` tant que le poller n'est pas en coupure soutenue. Ce numéro reste **figé** pour cette facture pendant toute la saisie (le worker continue de rafraîchir `base_connu` en arrière-plan pour la *prochaine* facture, jamais celle en cours) ; `self._numero_suggere` (côté vue) retient la valeur suggérée pour distinguer, au moment d'enregistrer, une correction manuelle du champ.
  3. **Au clic « Enregistrer » d'une NOUVELLE facture** (jamais en correction d'une facture existante, et jamais si le champ a été modifié à la main depuis la suggestion — `FacturationView._confirmer_numero_si_necessaire`) : un appel silencieux et à délai court confirme/ajuste le numéro — c'est le **seul** endroit avec un vrai verrou serveur (`POST /factures/reserver-numeros?quantite=1` → `NumeroResilientService.confirmer_numero`, `ApiSyncClient.reserver_numeros(1, delai_court=True)`). Réponse conforme ou différente (une autre facture créée ailleurs entre-temps) → le numéro confirmé est utilisé, sans que l'usager ne voie rien d'anormal. Échec/timeout → le numéro suggéré est gardé tel quel, **jamais bloquant** — mais inséré directement dans le pool local (`numeros_reserves`, comme s'il avait été confirmé) et `base_connu` avancé en conséquence, pour qu'un futur `suggerer_numero()` ne le reproprose jamais sans qu'une confirmation serveur n'ait jamais eu lieu (risque résiduel accepté, corrigible via le champ modifiable). Côté boss, `quantite=1` route vers `FacturationService.reserver_numero_jit` (voir ci-dessous) plutôt que `reserver_bloc_numeros` ; la route ajoute `n_postes_actifs`/`rang` à la réponse dans tous les cas (voir palier 2).
- **Reprise d'un numéro JIT abandonné** (`reserver_numero_jit`) : une confirmation qui ne débouche jamais sur une facture réellement enregistrée (app fermée entre-temps, échec applicatif après confirmation) consommait quand même le numéro pour de bon (règle historique : « on ne réémet jamais un numéro déjà distribué », y compris non consommé — voir `ReservationNumeroRepository`, docstring). Pour limiter ce coût sans relâcher la garantie d'absence de doublon : si la **toute dernière** réservation jamais faite (toutes machines confondues) est elle-même de **taille 1** (`numero_min == numero_max`, donc une précédente confirmation JIT — jamais un bloc de secours), **appartient à la machine appelante**, et **n'a donné lieu à aucune facture réelle** (`FactureRepository.dernier_numero() < ce numéro`), elle est proposée de nouveau au lieu d'avancer — cette réservation ne pouvant avoir été consommée par personne d'autre (exclusive à la machine qui l'a reçue). Volontairement restreint aux réservations de taille 1 : reprendre un BLOC (palier 2) serait risqué, le boss ne sachant pas combien de numéros de ce bloc la machine a déjà silencieusement consommés dans son pool local (`numeros_reserves`).
- **Bascule vers le palier 2/3** : uniquement si le **poller de fond** (palier 1, étape 1) échoue de façon soutenue pendant **20-30 s** (`EtatNumerotationRepository.coupure_soutenue`, seuil 25 s par défaut — vrai aussi tant qu'aucun sondage n'a jamais réussi, ex. démarrage sans serveur joignable) — signe d'une vraie coupure, pas d'un simple ralentissement isolé du contrôle ponctuel de l'étape 3. Dans ce cas, `suggerer_numero()` retombe sur le pool de secours local (`NumeroReservationRepository.prochain_disponible`) puis, s'il est également épuisé, sur le calcul déterministe (palier 3, `_calculer_bloc_local`) — la confirmation à l'enregistrement (étape 3 ci-dessus) reste, elle, toujours tentée quel que soit le palier ayant fourni la suggestion.
- **Palier 2 — Pool de secours local** : `NumeroReservationWorker` (`app/sync/numero_worker.py`) alimente en tâche de fond `numeros_reserves` (cache local) — **ne se déclenche que si `EtatNumerotationRepository.coupure_soutenue()` est vraie** (sinon la confirmation silencieuse du palier 1 suffit, inutile de maintenir un pool actif en permanence), une réserve pour absorber une coupure momentanée sans tomber immédiatement au calcul déterministe (palier 3). Taille de bloc `taille_bloc_secours(n)` : **N = 1 → 30**, **N ≥ 2 → 5 par poste** (plus petits pour limiter l'écart de numérotation en cas d'entrelacement) ; seuil de redemande = `max(1, bloc // 3)`. `N` (nombre de postes de facturation actuellement actifs) et le rang de ce poste sont communiqués par le boss à **chaque** réservation réussie (JIT ou bloc de secours) et persistés localement dans `etat_numerotation` (`EtatNumerotationRepository`, `app/sync/etat_numerotation.py`) : `n_connu`, `rang_connu`, `base_connu` (le plus haut numéro jamais vu localement, jamais rétrogradé), et `dernier_poll_reussi` (horodatage ISO UTC du dernier sondage réussi du palier 1). **Heartbeat sans requête dédiée** : `MachineActiviteRepository` (`app/repositories/machine_activite_repository.py`, table boss `machines_actives`) est mis à jour à chaque appel de `GET /referentiels/produits`/`GET /referentiels/clients`/`GET /factures/dernier-numero` et à chaque réservation de numéros — un poste sans requête depuis 60 s (`_FENETRE_ACTIVITE_SECONDES`) est considéré inactif. Le rang est la position de `machine_id` dans la liste des postes actifs triée par ordre alphabétique (déterministe, sans registre d'attribution explicite). **Démarrage sans serveur joignable** : `n_connu` vaut 1 par défaut (valeur initiale de `etat_numerotation`) tant qu'aucune réponse serveur n'a jamais été reçue — comportement le plus sûr (blocs contigus classiques, pas de partition).
- **Bug corrigé — `machines_actives` sur base boss PostgreSQL** : cette table, seule de tout le schéma sans colonne `id` à sa création, faisait échouer `ConnexionPostgres.execute()` (`app/repositories/db_backend.py`), qui ajoute automatiquement `RETURNING id` à tout `INSERT` pour émuler `lastrowid` — `column "id" does not exist`. Le heartbeat (`toucher()`, appelé à **chaque** `GET /referentiels/produits`/`clients` et à chaque réservation de numéros) levait donc une erreur serveur (500) systématiquement sur une base boss en PostgreSQL, cassant silencieusement **toute** la synchro descendante (nouveaux produits/clients, prix, stock jamais reçus par la machine de facturation) — l'erreur, catchée comme une simple `ErreurApiSync` par `ReferentielSyncWorker`, ne laissait aucune trace visible. Corrigé par une colonne `id` ajoutée à `machines_actives` (cohérent avec toutes les autres tables du schéma) ; `creer_connexion()` répare aussi, pour les bases déjà provisionnées avec l'ancienne forme, en supprimant la table bogée avant de la laisser se recréer correctement (`_corriger_machines_actives_postgres`) — sans perte réelle, cette table n'étant qu'un heartbeat entièrement reconstitué en quelques secondes.
- **Palier 3 — Continuation déterministe hors ligne** : si le pool de secours est également épuisé, `NumeroResilientService._calculer_bloc_local()` calcule un bloc entier **sans aucune communication réseau** : `bloc(k) = base_connu + 1 + (rang_connu + k × n_connu) × taille_bloc_secours(n_connu)`, où `k` (`prochain_k`, jamais réutilisé, jamais réinitialisé) avance à chaque appel de ce palier. Le `+ 1` est essentiel : `base_connu` est le plus haut numéro **déjà** utilisé/réservé — sans lui, le poste de rang 0 recalculerait littéralement `base_connu` à son tout premier bloc (k=0), réémettant le numéro d'une facture déjà existante (**bug corrigé** : sur une machine jamais encore synchronisée, `base_connu=0` par défaut, ce qui produisait carrément le numéro **0**, invalide, bloquant silencieusement tout enregistrement — voir `valider_entier_positif(strict=True)` — et empêchant du même coup la confirmation serveur de l'étape 3 du palier 1 de jamais s'exécuter, puisque `_lire_entete()` refusait la saisie avant même d'y arriver). Garantie : deux postes utilisant la même `base_connu` (apprise du serveur, donc partagée tant qu'ils ont été en ligne récemment) ne produisent jamais le même numéro, quel que soit l'ordre ou la simultanéité de leurs coupures — le calcul ne suppose jamais rien sur ce que fait l'autre poste (voir `tests/test_numero_resilient.py::test_appels_successifs_hors_ligne_ne_collisionnent_jamais_entre_deux_postes`, `test_suggestion_calcul_local_ne_reemet_jamais_le_numero_deja_connu`, `test_suggestion_machine_jamais_synchronisee_ne_suggere_jamais_zero`).
- **Corriger le calcul ne suffit pas à effacer une donnée déjà écrite avant le correctif** : sur une machine ayant déjà déclenché le bug ci-dessus AVANT le correctif, le numéro invalide (0) calculé à l'époque avait été inséré comme `disponible` dans `numeros_reserves` (cache local) — puisque jamais consommé (`_lire_entete` refuse toute saisie ≤ 0), il restait piégé dans le pool et `prochain_disponible()` continuait de le reproposer indéfiniment à CHAQUE suggestion (y compris après « Nouvelle facture »), même une fois le code corrigé et redéployé. Deux mesures : `base_repository._purger_numeros_reserves_invalides(conn)` (appelée à chaque `creer_connexion`, donc à chaque démarrage de l'app) supprime tout `disponible` avec `numero ≤ 0` résiduel ; `NumeroResilientService.suggerer_numero()` ignore désormais aussi, en mémoire, toute entrée `prochain_disponible()` ≤ 0 avant de la retourner (garde-fou redondant, indépendant de la purge). **`base_connu` n'est JAMAIS mis à jour à partir d'un calcul local** — seulement par une réservation/confirmation réussie côté serveur (palier 1 ou 2), ou par l'acceptation sans confirmation d'un numéro suggéré (`_accepter_sans_confirmation`, un numéro réellement consommé localement, pas une simple spéculation) : la mettre à jour à partir d'un CALCUL local (palier 3) ferait dériver les blocs suivants d'une base différente de celle des autres postes restés hors ligne, et casserait la garantie d'absence de collision. **Hypothèse simplificatrice assumée** : `n_connu`/`rang_connu` ne changent jamais pendant une coupure (pas de 3ᵉ poste qui s'ajoute, ni de poste qui disparaît en cours de route) — cas jugé suffisamment improbable pour ne pas être géré. **Interruption automatique** : dès que le poller de fond recommence à répondre (`marquer_poll_reussi`), `coupure_soutenue()` redevient fausse et `suggerer_numero()` reprend automatiquement le chemin instantané du palier 1 au prochain appel — aucun drapeau « mode hors ligne » à réinitialiser.
- **Unification de la consommation** : quel que soit le palier qui l'a fourni, le numéro retenu est inséré dans `numeros_reserves` (`ajouter_bloc`) avant d'être utilisé — `FacturationServiceHorsLigne.enregistrer_facture` continue de valider/consommer via `est_disponible`/`marquer_utilise`, inchangé, sans jamais avoir besoin de savoir quel palier a fourni le numéro ni si la confirmation serveur a réellement eu lieu.
- **`factures.numero` — contrainte UNIQUE côté base** (`idx_factures_numero_unique`, `base_repository._ajouter_contrainte_unique_factures_numero`, un index plutôt qu'une contrainte de colonne pour pouvoir l'ajouter après coup sans réécrire la table, ignorée silencieusement si des doublons existent déjà dans une base historique) : garde-fou final contre tout doublon résiduel, quelle que soit sa cause. Conséquence directe : deux factures ne peuvent plus jamais partager un numéro — la page Facturation (`_enregistrer`) refuse désormais catégoriquement (message d'erreur, plus de « Enregistrer quand même ? ») tout numéro déjà utilisé, l'ancienne tolérance datant du modèle usine/revendeur aujourd'hui supprimé (voir « Règles métier clés »).
- **Comportement transversal** : le numéro reste toujours un **entier pur**, jamais de marqueur visible. L'historique des ventes reste trié par **date/heure d'enregistrement**, jamais par numéro — un léger désordre numérique reste possible en cas de bascule entre paliers, mais sans jamais de doublon. Le paramètre `type_facture`, historiquement propagé dans ce sous-système, a été retiré des services/repositories publics ; les tables `reservations_numeros`/`numeros_reserves` conservent une colonne `type_facture` par défaut `'usine'`, laissée telle quelle à titre de détail interne inoffensif (jamais exposée dans une signature publique).

### Répartition boss/facturation-distante

`SMP.exe` peut lui-même devenir la machine de facturation à distance via un réglage (page « Paramètres machine », `config.definir_mode_machine("facturation_distante")`) plutôt qu'un exécutable dédié. `ApplicationFacturationEtendue` (`app/ui/app_facturation_etendue.py`) hérite de `ApplicationFacturation` et ajoute, **en direct par le réseau uniquement** : Historique complet, Archive, Paiements (lecture seule), Vue client. (Les anciennes entrées « Factures clients » et « Suivi des marges » de ce mode étendu ont été retirées avec la suppression de la notion de facture revendeur — voir « Règles métier clés ».)

## Règles métier clés

- **Numéro de facture — numérotation continue** : `suivant = max(numéros connus) + 1`, sans remise à zéro ni plafond, y compris pour la réservation de blocs.
- Une ligne de vente est valide si quantité > 0 et prix unitaire ≥ 0.
- **Il n'existe qu'une seule sorte de facture.** Le projet d'origine distinguait des factures « usine » (nos prix) et « client » (prix revendeur), avec un suivi de marge associé (« Suivi des marges ») et une hiérarchie de sous-clients rattachés à un revendeur — **ces trois fonctionnalités ont été intégralement retirées** (modèle, repositories, services, vues, endpoints API, synchronisation, tests) : cette entreprise ne facture pas de revendeurs et ne suit pas de marge d'intermédiaire. Une facture est identifiée par son numéro, sa date, son client, ses lignes, sa remise éventuelle et sa TVA (toujours 18 %).
- **Auto-création produit** : à l'enregistrement d'une facture, toute ligne dont la désignation ne correspond à aucun produit du catalogue (recherche par `designation`) crée le produit correspondant (sans option dimension/litrage, au prix pratiqué sur la ligne).
- **Robustesse** : `ui/app.py` surcharge `Tk.report_callback_exception` — toute exception imprévue dans un callback s'affiche dans une messagebox et se journalise dans `data/erreurs.log`.
- **Correction de données existantes** : la page Clients propose **Fusionner** (deux fiches doublons sont réunies : factures et remises du doublon transférés puis fiche supprimée). La page Produits propose une **recherche** (filtre live nom/valeur d'option) et **Fusionner** (réattribue les lignes de vente d'un doublon vers le produit conservé, puis le supprime).
- **Modification d'une facture déjà enregistrée** : `FacturationService.modifier_facture` (remplace en-tête + lignes, mêmes validations que la création, ne touche pas `archivee`, ré-applique correctement les mouvements de stock — voir « Gestion de stock ») évite de supprimer/ressaisir en cas d'erreur de saisie. Bouton **✎ Modifier** dans l'historique des ventes.
- **Proforma (brouillons)** : `models/proforma.py` (`Proforma`, sans champ `numero`) + `proforma_repository.py` + `proforma_service.py`. Un brouillon n'a **jamais** de numéro ; `ProformaService.valider(id, numero, date_facture)` le convertit en facture à part entière (délègue à `FacturationService.enregistrer_facture`) puis **supprime** le brouillon. Aucune contrainte d'unicité ni de rattachement client/produit tant qu'il reste un brouillon.
- **Archivage** : `factures.archivee` (0/1) masque une facture de l'historique des ventes **et** des statistiques/dashboards (`stats_service.py` filtre `archivee = 0`, sauf `ca_par_client`, volontairement non filtrée, utilisée par les Remises annuelles). Page dédiée **Archive** : sélection multiple, archivage/désarchivage par lot ou par période.
- **Chaque application gère son propre système d'archivage** : `factures.archivee` (app Facturation) ne se répercute jamais sur ce que voit un poste distant — `GET /factures` et les endpoints paiements appellent explicitement `inclure_archivees=True`. Le mode client gère son **propre** archivage, purement local (`app/client/archive_client.py`, fichier JSON, jamais envoyé au serveur).
- **Remise par facture** : `factures.remise_taux` (0 à 100) est distincte de la remise annuelle par client — certains clients négocient une remise appliquée à chaque vente plutôt qu'un taux annuel global. Propriétés calculées sur `Facture` : `total` (brut), `remise_montant`, `total_net` (montant dû, base de calcul de la TVA), `tva_montant`, `total_ht`, `total_ttc` (= `total_net`). Dans l'historique des ventes, la colonne « Total » affiche le montant net (après remise) et une colonne « Remise » indique le taux.
- **Export de l'historique** : `ExportExcelService.exporter_historique()` exporte les lignes filtrées de la page Historique (une seule sorte de facture, plus de paramètre de type).

## 3. Conventions et commandes

### Commandes (PowerShell, à la racine du projet)

```powershell
python -m app.main             # Lancer l'app Facturation (machine boss)
python -m app.api.server       # Lancer le serveur API seul (accès distant, bloquant)
python -m app.main_client      # Lancer l'app Client/Serveur (poste distant)
python -m app.main_stock       # Lancer l'app Stock (poste dédié à l'entrepôt)
python -m app.main_facturation # Lancer ApplicationFacturation seule (dev/debug — plus packagée en .exe)
python -m pytest tests/ -v    # Lancer les tests
python -m pip install -r requirements.txt   # Installer les dépendances
# Générer l'exécutable Windows principal (dist\SMP.exe) :
python -m PyInstaller --noconfirm --clean --onefile --windowed --name "SMP" --icon "app/icone.ico" --add-data "logo.png;." app/main.py
# Générer l'exécutable serveur autonome (dist\SMP-Serveur.exe) :
python -m PyInstaller --noconfirm --clean --onefile --windowed --name "SMP-Serveur" --icon "app/icone.ico" --add-data "logo.png;." app/main_server.py
# Générer l'exécutable client (dist\SMP-Client.exe) :
python -m PyInstaller --noconfirm --clean --onefile --windowed --name "SMP-Client" --icon "app/icone.ico" --add-data "logo.png;." --hidden-import psycopg2 app/main_client.py
# Générer l'exécutable Stock (dist\SMP-Stock.exe) — le plus léger,
# aucune ressource embarquée nécessaire (pas de PDF/logo généré par cette app) :
python -m PyInstaller --noconfirm --clean --onefile --windowed --name "SMP-Stock" --icon "app/icone.ico" app/main_stock.py
```

`SMP-Facturation.exe` n'est pas généré/distribué (redondant avec `SMP.exe` en mode `facturation_distante`) — `app/main_facturation.py` reste utilisable en source pour du développement ciblé.

En exécutable (`sys.frozen`), `config.py` place les données dans `data\` à côté du .exe et lit le logo depuis les ressources embarquées (`sys._MEIPASS`).

`SMP.exe` (GUI) n'importe **jamais** FastAPI/uvicorn en statique — `ApiManagementService.demarrer()` lance `SMP-Serveur.exe` comme processus séparé. Seul `SMP-Serveur.exe` les embarque.

### Nommage

- Fichiers/fonctions/variables : `snake_case` ; classes : `PascalCase` ; constantes : `UPPER_SNAKE_CASE`.
- Vues : suffixe `View` ; services : suffixe `Service` ; repositories : suffixe `Repository`.
- Clés i18n : `snake_case` groupé par domaine (`facture_titre`, `dashboard_ca_jour`, `stock_*`…).

### Gestion des erreurs

- Exceptions métier personnalisées dans `utils/validation.py` (`ErreurMetier`, `ErreurValidation`, `ErreurImport`) — messages en clair, traduits au niveau UI.
- Les services lèvent ; l'UI attrape et affiche (toast/messagebox), jamais de traceback à l'utilisateur.
- Les repositories utilisent des transactions ; toute écriture multi-tables (facture + lignes + mouvements de stock, par exemple) est atomique.

### Dépendances (épinglées dans requirements.txt)

`reportlab` (PDF), `matplotlib` (graphiques), `tkcalendar` (sélecteur de date calendrier), `fastapi`/`uvicorn` (API distante), `requests`/`httpx` (clients HTTP), `psycopg2-binary` (bascule PostgreSQL), `pytest` (tests). Tkinter/sqlite3 : bibliothèque standard. Python ≥ 3.10.

`openpyxl` n'est conservé que pour l'export Excel de l'historique (`export_excel_service.py`) — l'import Excel du classeur historique de l'ancienne entreprise (`facture.xlsm`) a été retiré, propre au système d'origine et sans équivalent pour cette société.
